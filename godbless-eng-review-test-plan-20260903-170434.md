## Test infrastructure (locked)

- Vite + React + TypeScript client, @supabase/supabase-js.
- Supabase local (supabase start) runs the real Postgres + Edge Functions for
  integration tests of every RPC and scoring function.
- Vitest for unit + integration. Playwright for exactly ONE full-room E2E smoke.
- Gate tests are local, deterministic, <2s (AGENTS.md rule).

## Affected Pages/Routes

- `/instructor` — quiz authoring: questions, correct answers, pacing (auto per-question
  duration vs manual), winner count. Verify saving then starting a quiz.
- `/instructor/room/:id` — live room control: start, next tap (manual), standings view,
  podium reveal.
- `/join` + room link/QR — player join: email, nickname, avatar grid; lobby wait.
- `/play/:roomId` — timed question, countdown from started_at, answer buttons, live
  standings.
- `/podium/:roomId` — top N winners with amounts; each winner sees on-screen
  redemption options WITHOUT opening email first.

## Key Interactions to Verify

- Instructor authors quiz with correct answers stored server-side, starts room, players
  join via QR.
- All players see the same question at the same second (server-stamped started_at), and
  the countdown renders from that epoch.
- In MANUAL mode, no next question appears until instructor taps next; in AUTO mode,
  the server schedule advances without any client tab awake.
- A late answer (now >= started_at + duration) is REJECTED by the Postgres RPC.
- Clock-skew correction: a client with a deliberately wrong clock (simulated +20s lag)
  renders the true remaining time via the server-offset measurement, not its own clock.
- Standings update live from the server-side standings row as answers are accepted.
- Podium declares top N winners; each winner's current screen shows redeem options;
  clicking one creates exactly ONE claim (idempotent RPC) and surfaces a claim_code
  delivered only to that winner's session.
- Redeeming requires claim_code + matching email + participant id; a wrong code or a
  different email is rejected. The closing persona's transfer reaches COMPLETED via
  the single Edge Function settlement.
- Non-persona winners reach a uniform terminal beat ("invite sent — complete
  onboarding"), never a permanent processing state.
- Redemption email is sent after claim success; provider failure logs to the instructor
  dashboard and never blocks the on-screen flow.
- Broadcasts and the projector never expose winner emails or claim_codes.

## Edge Cases

- Double-tap / replay of the redeem button creates exactly one claim, one invite.
- Player phone dies, rejoins with same email: resumes SAME participant, same score,
  one claim slot; no double-count in standings.
- Two devices, same email: first answer stands, second treated as same participant.
- Player joins mid-question: enters at the current question with zero backlog.
- Player answers the same question twice: second answer rejected, first stands.
- Tie at the winner boundary: deterministic order (correct count, then cumulative
  speed, then earliest join) decides; no manual podium dispute.
- Venue wifi drop mid-question: NoSleep + rejoin resyncs to authoritative question +
  remaining time from the server row.
- Phone clock is 20s slow: countdown still ends when the server bell rings (offset
  correction), and a genuinely late answer is still rejected.

## Critical Paths (must work at the venue)

- Full room: join (QR) → lobby → timed question → answers land live → standings move →
  MANUAL advance → podium top-N with amounts.
- Money loop (seeded room): winner taps redeem on-screen → claim_code validates →
  exactly one claim → single Edge Function settlement → sandbox transfer COMPLETED →
  email logged. Judges must see the pool balance move.
- Uniform terminal state for non-persona winners: claim recorded + invite sent, no
  dead-end processing screen.
- Rejoin safety: a dropped phone lands back on the current question with correct
  remaining time.

## Failure modes to watch

- Silent money failure: if a redeem tap errors and shows nothing, that is a critical
  gap. Claim must surface state (pending/invited/paid) on the winner screen.
- Stale leaderboard after rejoin: standings must be server-owned, not client-assembled.
- AUTO room stalling: must not depend on any client tab; server schedule is the only
  advance authority.
